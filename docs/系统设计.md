# 集中管理系统 · 系统设计

> 面向三个既有单文件工具的整合方案：现状分析、技术选型、数据模型、联动规则与接口设计。

---

## 1. 三个旧项目的现状

| | **SalesContract**（销售合同） | **Contract-Generator**（报价单） | **delivery-note-generator**（送货单） |
|---|---|---|---|
| 形态 | 单个 HTML（约 486 KB），JS/CSS 内联，logo 与合同章 base64 | 单个 HTML（约 1.27 MB），3 套 logo + 3 枚章内嵌 | 单个 HTML（约 140 KB）+ bat/ps1 启动脚本 |
| 用途 | 产品销售合同，A4 一页 | 报价单，A4 一页 | 送货单，241×140 三联纸 + A4 |
| 数据存放 | 浏览器 localStorage | 浏览器 localStorage | 浏览器 localStorage |
| 主要键 | `sc-contract-draft-v1`、`-recs-v1`、`-clients-v1`、`-prod-v1`、`-stamp-v1`、`-seq` | `ac-quote-draft-v1`、`-recs-v1`、`-clients-v1`、`-prod-v1`、`-opts-v1`、`-seq`、`-stampup-v1` | `shd_records_v1`、`shd_lib_v1`、`shd_settings_v1`、`shd_draft_v1` |
| 单据记录上限 | 200 条 | 500 条 | 500 条 |
| 客户档案 | 对象，按名称存 `{addr, rep, phone}`，最多 200 家 | 数组，`{name, contact, phone, fax, about}`，最多 200 家 | 无独立客户库，只有输入历史 |
| 货品库 | `[{spec, name}]`，1000 条 | `[{spec, name}]`，1000 条 | `spec → {name, unit}`，1000 条 |
| 公司主体 | jxt / yzl / ac（编号前缀 JXT/YZL/AC） | jxt / yzl / anc / none | 无，默认「开异」抬头 |
| 编号 | `JXT-20261127-001` | `AC-20261127-001` | `XS-2026-11-25-00003`（XS/DB/TQ 分流水） |
| 部署 | nginx 静态容器，端口 8091，GH Actions + Watchtower | 同左，端口 8090 | 同左，端口 8088；另有源码同步模式 |
| 输出 | 打印 / PDF / 可编辑 .docx | 打印 / PDF / 可编辑 .docx | 打印 / Excel |

### 共同优点（要继承的）

- **版式打磨得很细**：A4 留白做进内容、打印面板选「边距=无」也不贴边、明细只打印真正填过的行、合计/大写准确
- **录入效率高**：Excel 批量粘贴、回车跳行、规格联想带出品名、客户下拉带出联系方式
- **零安装**：双击 HTML 就能用，断网也能开单
- **备份可迁移**：JSON 导出 / 导入，章图可随备份走

### 共同问题（本次要解决的）

1. **数据锁在个人浏览器里**：localStorage 按「协议 + 地址 + 端口」隔离，同事之间不互通；换电脑、清缓存、换 IP 都会「丢数据」，只能靠手工导出/导入搬家
2. **同一份客户资料存了三份**：三个工具的客户库结构不同（`contact` vs `rep`、报价单多 `fax/about`、送货单没有客户库），名字一样却各记各的，越用越不一致
3. **三张单之间没有关系**：报价单签下来要手工重录成合同，合同发货又要手工重录成送货单，重复劳动且容易错行、错价
4. **没有账号与权限**：谁都能改、能删；没有操作记录，出问题查不到
5. **文件没有归口**：合同扫描件、发票、送货回单散落在电脑文件夹里，和单号对不上
6. **统计靠人脑**：这个月报了多少、哪张报价还没转合同、哪张合同还没送货，只能翻记录

## 2. 目标与不做什么

**目标**

- 一个地址、一套账号，多人共用同一份客户 / 货品 / 单据 / 文件
- 报价 → 合同 → 送货单 一条链，下游自动继承上游数据，不再重录
- 数据在服务器，备份 = 拷一个目录
- 保留「开单 → 打印」这条主路径的体验，不因为上了系统而变慢

**本期不做（避免过度设计）**

- 不做完整 ERP（库存、采购、应收应付、财务凭证）
- 不做审批流引擎（先用「状态 + 待跟进列表」覆盖）
- 不做像素级复刻旧工具的所有版式微调（列宽拖拽、字号系数、Word 导出放二期）
- 不做多租户 / 对外门户

## 3. 技术选型

```
浏览器（原生 ES Module 单页）
   │  HTTPS / JSON + multipart
   ▼
Node.js 22 HTTP 服务（零第三方依赖）
   ├── 路由 + JWT 登录 + 角色校验 + 审计
   ├── 业务层：单据编号、客户/货品自动建档、单据联动
   ├── node:sqlite（app.db，WAL）
   └── 文件落盘 data/files/年-月/
```

**选 Node.js 的理由**

1. 三个旧工具都是 JavaScript，金额大写、A4 版式、打印逻辑可以平移，不需要「翻译」一遍
2. 前后端同语言，一个人维护得住；没有 npm 依赖，升级不怕供应链
3. Node 22.5 起内置 `node:sqlite`，不用装数据库、不用编译原生模块（Windows 上尤其省事）
4. 单进程 + 单目录，Windows 双击 bat、NAS 一个容器都能跑；数据备份就是拷 `data/`
5. 以后要换库，只改 `src/db.js` 一个文件

**为什么不是 MySQL/PostgreSQL**：这套系统是「几个人、一天几十张单」，SQLite 的写入能力远超需求；引入数据库服务只会让 NAS 部署、备份、迁移变复杂。等真出现多实例/高并发再换。

**为什么前端不用 Vue/React + 构建**：页面数量有限（9 个），原生 ES Module 已按页面拆成 `web/assets/js/pages/*`，省掉 node_modules 与构建链，改一行 CSS 刷新即可见，部署时也不用先 `npm run build`。如果后续单个页面复杂度上来，可以只把那一页换成 Vue，不影响其他页面和后端。

## 4. 数据模型

```
users ── owner_id ── customers / documents / files
companies ── logo_file_id / stamp_file_id ── files
customers ─┬─ customer_id ── documents
           └─ customer_files ── files
documents ─┬─ document_files ── files
           └─ parent_id / root_id ── documents（单据链）
products（独立，开单时联想）
number_seq（按 公司-YYYYMMDD 计跨类型流水）
audit（操作日志）
```

### 4.1 表结构

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | username(唯一，支持中文), name, password(旧字段，v1.7 起不校验), role, active | 免密码身份；用户名 2–24 位，中文/字母/数字/`_`/`.`/`-` |
| `companies` | code, name, addr, rep, phone, fax, logo_file_id, stamp_file_id | 三家主体，编号取 code |
| `customers` | name + created_by(联合唯一), addr, contact, phone, fax, tax_no, note | 统一客户档案，归属人为 `created_by`；`note` 支持多行，记录付款方式、账期、成本加点等 |
| `products` | name + spec(全库联合唯一), unit, price, note, owner_id | 全系统共享货品库；`owner_id` 只用于标识创建人，不参与列表隔离；只有创建人可改删 |
| `documents` | doc_no(不唯一，业务链可共享), type, status, company_id, customer_id, owner_id, doc_date, amount, tax_rate, payload(JSON), parent_id, root_id, warehouse_status, warehouse_at/by, warehouse_received_at/by, deleted_at/by | 三种单据一张表，差异放 payload；归属人 `owner_id`；仓库流转与软删除字段用于 v1.8 |
| `files` | name, stored, mime, size, sha256, category, owner_id, deleted_at/by | 文件元数据，实体在磁盘；归属人 `owner_id`；删除为软删除 |
| `document_files` | document_id, file_id, category | 单据附件关联 |
| `customer_files` | customer_id, file_id, category | 客户档案附件关联，支持付款资料、客户信息、合同扫描件等 |
| `number_seq` | key, n | 编号流水，按 `JXT-20261128` 跨单据类型共享计数 |
| `audit` | user_id, action, target, detail, ip | 登录、增删改、导入 |

### 4.2 为什么单据用「公共列 + payload JSON」

三种单据的**头信息**高度相似（编号、日期、客户、金额、状态），但**明细与条款**差别大：

- 报价单：`validDays / taxMode / terms{delivery,invoice,extra} / stamp / cols`
- 合同：`signDate / terms[{label,text,on}] / termNumbered / stamp`
- 送货单：`dtype / customer / items{code,proj,unit,pin,contract}`

如果强行拆成三张表，联动、统计、列表都要写三套；全部塞进宽表又会有一堆空列。
所以：**可查询、可排序、可统计的字段提成列**（编号/类型/状态/客户/日期/金额/主体/负责人/父子关系），**版式细节留在 payload**，打印时原样渲染。这样既保留了旧工具的数据结构（迁移几乎零转换），又让列表、统计、联动都能走 SQL。

### 4.3 单据链

- 新建时 `root_id = 自己的 id`
- 「转合同 / 转送货单」时：`parent_id = 源单 id`，`root_id = 源单的 root_id`
- 链路查询：取 `root_id` 相同的全部节点，前端按 `parent_id` 组装成横向流程图
- 一条链允许分叉（一张报价转多张合同、一张合同分多次送货），详情页用圆角卡片和箭头展示分支：报价单在左，合同在中间，送货单接在对应合同右侧
- 单据中心列表按 `root_id` 分组：同一业务链的单据放在“关联单据”标题下，组内按报价 → 合同 → 送货单排列；“关联”列显示直接上下游关系，方便从列表识别同组单据
- 列表分页以 20 张为页容量，但先按 `root_id` 聚合再分页：同一条链尽量整组放进同一页；单条链超过 20 张时整链单独占一页，不会被分页截断
- 列表筛选支持 `q`（单号/标题/客户）、`status`、`from/to`、`customer_id` 和 `quick`；`quick` 取值 `quote_no_contract`、`contract_no_delivery`、`delivery_pending`、`delivery_received`

### 4.4 编号规则

`{公司代码}-{YYYYMMDD}{3位流水}`，例如 `JXT-20261128001`。

- 同一公司、同一天，报价单、销售合同、送货单共用一条流水；001 被任何类型使用后，下一个新单据从 002 开始。
- 流水键 = `公司-YYYYMMDD`；新建时可预览，保存时在事务里正式占号。
- 第一次报价转合同、报价/合同转送货单时，新单据继承源单 `doc_no`，不重新占号；因此同一条业务链上的第一张下游单据编号相同。
- 如果同源单据已经生成过合同/送货单，详情页会提示“覆盖原单”或“另存新单”：
  - 覆盖：保留原下游单据编号，用源单内容更新最近一张下游单据。
  - 另存：从源单编号末三位往后递增（001 → 002 → 003…），并逐个检查全系统是否已有单据占用该编号，跳过已占用编号，使用第一个未占用编号。
  - 报价单转送货单时，如果整条链路（包括各合同下）已经有送货单，会提示确认；继续生成的新送货单使用未占用编号，避免重复单号。
- `documents.doc_no` 不设唯一约束，编号唯一性只针对新建占号；手动改编号时仍会检查是否已被其他单据占用。

## 5. 联动规则（核心）

| 方向 | 带过去的内容 | 不带 / 重置 |
|---|---|---|
| 报价单 → 合同 | 客户名称/地址/联系人/电话、全部明细（品名/规格/数量/单价）、税率、备注 | 合同编号重新生成；签订日期留空；条款换成合同默认五条；电子章默认开启 |
| 合同 → 送货单 | 客户名称、明细（品名/规格/数量），并在每行写入关联合同号 | 送货单编号重新生成；单位留空可补；金额列不打印 |
| 报价单 → 送货单 | 同上（小额直接发货的场景） | 关联合同号为空 |

**不做自动同步**：下游单据是独立快照。上游改价不会改已签的合同——这符合纸质单据的业务习惯；需要改就改下游单据本身，链路只负责追溯。

**上游锁定**：一旦单据已经派生下游（`parent_id` 指向它且未删除），上游的客户、明细、金额、日期、编号、税率、供货主体、条款等内容锁定。`PUT /api/documents/:id` 会比较新 payload 的指纹，只允许改状态、备注和附件；详情页在原单据上显示锁定提示，并提供“编辑备注”入口。版式字段（Logo、电子章位置、签章栏、列宽、字号）不参与锁定，方便只调整打印样式。合同已有未删除的送货单时，报价单不能再“覆盖”该合同，只能另存新合同。

**客户 / 货品的沉淀**：任何单据保存时，按 `(归属人, 客户名)` upsert 客户档案（只补空字段，不覆盖已有电话/地址），按 `(归属人, 品名 + 规格)` upsert 货品（价格取最近一次非零值）。

## 6. 权限与数据隔离

| 角色 | 数据可见范围 | 能力 |
|---|---|---|
| `admin` 管理员 | 全部成员，可按成员切换 | 唯一拥有全部权限：跨成员查看/编辑/打印/改状态/删除/转换 + 用户管理 + 公司主体/章 + 导入旧数据 + 导出备份；仓库流转中的送货单只读，接收/编辑/完成仅仓库账号 |
| `sales` 业务员 | 仅本人 | 本人开单、改单、传附件；送货单可提交/撤回仓库，提交后接收前不能编辑；无系统设置和用户管理 |
| `warehouse` 仓库 | 仅已提交仓库的送货单 + 本账号自建送货单 | 接收、编辑、打印、完成；待接收单可直接打印，打印时自动接收为“处理中”；可手动新建送货单，保存后直接进入“处理中”；不能新建报价单/合同，不能改归属、业务状态或派生单据；登录后只显示仓库打单 |
| `guest` 游客 | 仅本游客身份 | 本人三单/客户/货品/文件；用户与主体管理不可用 |

- 服务端统一用 `src/scope.js`：`requestedOwner()` 普通用户强制本人，管理员不带 `owner` 看全量、带 `owner=<id>` 看指定成员；`assertOwner()` 对单据/客户/货品/文件做归属校验，非管理员访问他人数据直接返回 404。
- 客户按 `created_by` 隔离，货品、单据、文件按 `owner_id` 隔离；统计（工作台、客户累计金额、单据数）同样按 owner 过滤。
- 管理员跨成员编辑单据时，`ensureCustomer / saveProducts` 使用单据原 owner，不会把客户/货品建到管理员名下；代转下游单据也继承源单 owner。
- 公司 Logo / 电子章属于公司共用资源，`isCompanyAsset()` 放行所有登录账号读取。
- 用户名规则：`^[\p{L}\p{N}_.-]{2,24}$`，公开注册默认 `sales`，注册成功直接登录；登录只匹配用户名，不校验密码。
- v1.15 移除 `manager` 主管身份，只保留管理员、业务员、仓库和游客；历史 `manager` 账号在服务启动时按最小权限自动转为 `sales`。系统设置、导入旧数据、导出备份、公司主体/章统一仅管理员可用。

### 6.1 游客模式（兼容入口）

游客不是本地草稿，而是一个**服务端临时账号**，只拥有该游客身份名下的客户、货品、单据、文件，其他账号看不到。

| 维度 | 游客 | 登录用户 |
|---|---|---|
| 身份 | 持久化 cookie `gid`（UUID，一年，HttpOnly/SameSite=Lax）↔ `users.role='guest'` 行 | Bearer token |
| 开单 / 打印 | 三单全部可开可打，内置 Logo / 电子章直接可用 | 同 |
| 数据范围 | 仅本游客身份 | 仅本人；管理员可看全部 |
| 用户管理 / 公司主体 / 系统设置 | 不开放 | 开放 |

**登录/注册合并（一次性）**

1. 登录或注册请求读取 `gid` cookie，找到对应 `guest` 用户；
2. 事务内把该游客的 `documents.owner_id`、`files.owner_id` 改成登录账号；客户按 `(created_by,name)` 合并，货品按 `(owner_id,name,spec)` 合并；
3. 删除该 `guest` 用户行，并下发 `gid` 过期 cookie；
4. 返回 `merged` 计数，前端提示合并了多少单据/文件/客户/货品。

合并后游客身份已不存在，**同一浏览器再登录另一个账号时找不到可合并的游客数据**，不会二次合并；单据归属保持第一个账号，清 cookie 也不影响。

### 6.2 仓库流转（v1.8）

只有 `type='delivery'` 的送货单走仓库流程，字段 `warehouse_status` 取值：

| 值 | 含义 | 触发 |
|---|---|---|
| `none` | 未提交 | 默认 |
| `pending` | 待接收 | 业务员（制单人）点“交仓库”；仓库可直接打印，打印前自动接收 |
| `received` | 处理中 | 仓库账号接收后，可编辑、打印 |
| `done` | 已完成 | 仓库账号点“完成” |

权限由 `canAccessDocument()` 控制：管理员和单据 owner 始终可访问；仓库角色只能访问 `type='delivery'` 且 `warehouse_status<>'none'` 的单据，其他数据返回 404。管理员进入仓库页只读查看队列；接收、编辑、打印、完成仅仓库账号可操作。业务员提交后、仓库接收前只能撤回，不能编辑；`pending` 状态下任何人都不能编辑。仓库编辑使用 `PUT /api/documents/:id`，但不改变 `owner_id`；仓库不能改业务状态、不能派生下游单据、不能删除单据。仓库可通过 `POST /api/documents` 新建 `type='delivery'` 的单据，创建后服务端自动把 `warehouse_status` 置为 `received`，因此不需要业务员提交或仓库接收；仓库新建报价单/合同仍返回 403。

### 6.3 回收站（v1.8）

单据和文件删除不再立即物理删除，改为写 `deleted_at / deleted_by`：

- 单据删除保留 `document_files` 关联，回收站恢复后附件仍可见；
- 文件删除只标记，实体文件仍在磁盘；
- 回收站保留 30 天，`src/recycle.js` 的 `purgeRecycleBin()` 在服务启动时和每 6 小时执行一次，到期后：
  - 单据：先删 `document_files` 关联，再删单据行，附件实体不删；
  - 文件：删磁盘实体、`document_files` 关联和文件行；
- 普通用户只能看到、恢复、永久删除自己的条目；管理员可看全部，并可按 `?owner=<id>` 筛选；
- v1.14 起每张回收站单据可 `GET /api/recycle/documents/:id` 只读查看：返回客户、明细、备注、附件、删除人、删除时间和剩余保留天数；前端用弹窗展示，永久删除前先核对内容，避免误删；
- 回收站列表也支持在列表前顺手清理到期条目，避免长时间无请求时残留。

实现要点：

- `src/auth.js`：`getOrCreateGuest()` 负责发/复用 cookie 并建 guest 用户；`mergeGuestData()` 做一次性转移；`currentUser()` 在无 token 时回落到游客身份
- `src/routes/auth.js`：`GET /api/auth/guest` 游客入口；`POST /api/auth/login` 免密码登录；`POST /api/auth/register` 公开注册
- 前端：`boot()` 无 token 先渲染登录/注册页，页底保留“临时游客模式”；登录后进入本人工作台

### 6.4 本地草稿保护（v1.13）

长报价单在模板 iframe 内编辑，浏览器崩溃、误关或直接点“返回系统”都可能丢掉未保存内容。v1.13 增加一层纯前端草稿：

- 存储位置：父页面 `localStorage`，键 `__central_unsaved_draft_v1_<user_id>_<type>_<docId|new>`，按账号和单据隔离，避免同一浏览器换账号后看到别人的草稿；
- 暂存时机：模板监听 `input / change / paste / pointerup`，停止输入 600ms 后取当前模板状态；打开后 350ms 建立基线，只有状态与基线不同才在 250ms 后发给父页面，避免初始化产生假草稿；
- 恢复：重新进入同一张单时比较草稿 `savedAt` 与服务端 `updated_at`；服务端更新则静默丢弃，否则弹“发现未保存的本地草稿”，提供“恢复草稿 / 放弃草稿 / 暂不恢复”；恢复时通过 `seed(ed, autoPrint, draftState)` 覆盖模板初始数据；
- 清理：保存或打印回写成功后同时清除 `new` 与真实 `docId` 两个键；放弃草稿立即删除；超过 14 天未处理的草稿在打开编辑器时清理；锁定单据不再读取草稿并删除旧键；
- 容量：单份草稿序列化后超过 1MB 不写入，避免挤占 localStorage；写入失败只影响草稿，不阻断编辑；
- 边界：草稿只存在当前浏览器，换电脑/换浏览器/清站点数据都不会带过去，也不替代服务端保存。

实现入口：`template-bridge.js` 的 draft 消息与基线、`template-editor.js` 的 `saveDraft / readDraft / askRecoverDraft`。

## 7. 文件存储

- 上传走 `multipart/form-data`，单文件上限 100 MB
- 落盘：`data/files/YYYY-MM/<uuid><ext>`，数据库存相对路径、原始文件名、MIME、大小、SHA-256
- 访问：`/api/files/:id/raw`（inline，可预览图片/PDF）、`/download`（附件下载）
- 引用保护：被单据或公司主体引用的文件不允许删除
- 备份：整个 `data/files` 目录 + `app.db`

## 8. 旧数据迁移

系统设置 → 「从旧工具导入数据」，直接选旧工具导出的 JSON：

| 来源 | 识别 | 映射 |
|---|---|---|
| 报价单「导出全部」 | `kind: "ac-quote-all"` | `recs[].data` → 报价单；`clients[]` → 客户；`prod[]` → 货品 |
| 合同「导出备份」 | `kind: "sale-contract"` | `recs[].st` → 合同；`clients{}` → 客户；`prod[]` → 货品 |
| 送货单「导出备份」 | `type: "送货单生成器备份"` | `records[].data` → 送货单；`products.t` / `library` → 货品 |
| 单张草稿 JSON | 含 `items` + `cust`/`customer` | 按有无 `dtype` 判断报价单或送货单 |

规则：单据按编号去重（已存在则跳过），客户按名称去重，货品按「品名+规格」去重；导入状态分别标为 已发出 / 已签订 / 已签收，方便在工作台看到历史盘子。

## 9. 部署形态

|---|---|
