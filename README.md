# 集中管理系统（报价 / 合同 / 送货单）

> 当前版本：**v1.10.1**（2026-11-28）

把原来三个「单文件 HTML + 浏览器 localStorage」工具的数据，统一收拢到一台服务器上：
**一套客户档案、一套货品库、一条报价 → 合同 → 送货单的业务链、一个文件库、一套账号权限**。
每个账号只看到自己的工作台、客户、货品、单据和文件；管理员可以查看全部成员，并按成员切换工作台。

- 后端：Node.js 22 + 内置 `node:sqlite`（零第三方依赖，不需要 npm install）
- 前端：原生 ES Module 单页（无构建步骤，改完刷新即生效）
- 部署：Windows 直接 `node server.js`；NAS / 服务器用 Docker，数据挂载到 `./data`
- 详细部署步骤（飞牛 fnOS Docker / Windows、更新、迁移、备份、常见报错）见 [`docs/部署说明.md`](docs/部署说明.md)

## 一、为什么选 Node.js

| 方案 | 结论 |
|---|---|
| **Node.js + SQLite（本项目）** | 和三个旧工具同为 JavaScript，金额大写、A4 版式、打印逻辑可以原样搬；前后端一套语言；Node 22 自带 SQLite，单进程 + 单目录就能跑；NAS / Windows 都合适 |
| Python + FastAPI | 也能做，但前后端两套语言、两套依赖，单人维护成本高 |
| Java / Spring Boot | 对这套「几个人用、一天几十张单」的体量太重，部署要 JVM + 数据库 |
| PHP | 传统表单友好，但实时明细行、打印预览这类交互要另写大量 JS |
| Go | 性能好，但开发速度慢，且打印/表格类前端仍要 JS，等于两套语言 |

**结论：Node.js（JavaScript 全栈）+ SQLite 起步。**
现在的数据量（客户几百家、单据几千张）SQLite 完全够用；以后真要上多人高并发，`src/db.js` 是唯一的数据访问层，换 PostgreSQL 不用改业务代码。

## 二、功能

**免密码账号（默认）**
- 登录只凭用户名，不校验密码；用户名支持中文、字母、数字、下划线、点或短横，2–24 位
- 任何人可在登录页自助注册，默认业务员角色；业务员没有“系统设置”和“用户管理”，系统设置仅管理员/主管可见，用户管理仅管理员可见；管理员账号仍叫 `admin`，同样免密码登录
- 每个普通账号只能看到自己的客户、货品、单据、文件和统计；前端与后端双层按 `owner_id/created_by` 隔离
- 管理员默认看到全部成员的数据，可通过工作台、单据、客户、货品、文件页的成员下拉切换；管理员可查看、编辑、打印、改状态、删除、转换任意成员的单据（仓库流转中的送货单除外，接收、编辑、完成仅仓库账号可操作）
- 管理员在“查看某个成员”时不提供新建入口，避免把新单建到自己名下；切回“全部成员”即可新建

**游客模式（兼容入口）**
- 登录页仍保留“先不登录，用临时游客模式”；游客身份由持久化 cookie `gid` 标识，服务端为它建一个临时 `guest` 账号
- 游客数据只属于该浏览器对应的游客身份，其他账号看不到；注册/登录时自动合并到账号，合并后删除游客身份
- 游客只能操作自己的数据，不能进入用户管理

**客户档案**
- 新增 / 编辑 / 搜索；名称、联系人、电话、传真、地址、税号、备注
- 客户备注支持多行，可记录付款方式、账期、成本加点、开票要求等
- 客户详情可上传付款资料、客户信息、合同扫描件等附件，支持查看、下载、移除
- 开单时输入客户名自动建档、自动补全联系方式；客户详情页汇总全部往来单据与合同金额

**界面与手机适配**
- 窗口变窄或手机访问时，侧栏自动变为顶部品牌 + 可横向滑动的导航，页面内容占满屏幕
- 表格设置最小宽度，窄屏时在卡片内左右滑动查看，不再压缩重叠；统计卡在手机端改为两列
- 报价单、销售合同、送货单编辑器在手机端改为上下排列：录入区在上、打印预览在下，明细表可横向滑动；界面最小按 320px 宽度适配

**货品库**
- 品名 + 规格型号 + 单位 + 参考单价；开单时在「规格型号」输入即带出品名与单价
- **全系统共享**：所有账号都能查看和使用全部货品；但只能修改或删除自己创建的货品，其他人创建的货品为只读
- 同一品名 + 规格型号全库唯一，明细填齐后自动入库，不会按账号重复建档

**单据中心**
- 报价单 / 销售合同 / 送货单，各自独立状态
- 编号规则：`公司代码 + 日期 + 三位流水`，例如 `JXT-20261128001`；同一公司同一天，报价单、合同、送货单共用一条流水，001 被用后下一个自动从 002 开始
- 单据中心按业务链分组：同一 `root_id` 的报价、合同、送货单折叠在“关联单据”标题下，组内按报价 → 合同 → 送货单排列；不同成员的单据仍按原权限隔离，所以编号可能有跳过，例如 002 被其他人占用时下一张直接用 003
- 第一次报价转合同、合同/报价转送货单时，新单据**继承原单据编号不变**；如果同一源单已经生成过合同/送货单，点转换会提示“覆盖原单”或“另存新单”。另存时从源单编号往后递增，并检查全系统占用情况，跳过已用编号；覆盖保留原下游单号
- 历史上已生成的旧格式编号（如 `JXT-BJ-20261128-013`）保持原样，不改写；新格式只用于之后新建的单据
- 明细支持 Excel 粘贴、行增删、合计与人民币大写
- 新建 / 编辑单据时直接打开原来的三套生成器网页，表单、A4 预览、打印、条款与签章保持模板原生效果；客户、货品、公司抬头、单号与正文数据由集中系统注入，模板保存/打印时自动回写服务器
- 生成器网页副本在 `web/templates/`（报价 `quote.html`、合同 `contract.html`、送货 `delivery.html`），由原文件复制并追加 `template-bridge.js`；原模板后续如有改动，需要把这几个文件重新复制过去
- 旧的集中式编辑工作台保留为兼容入口：`#/doc/new?type=quote&classic=1`

**三单联动（核心）**
- 报价单 → 一键「转合同」：客户、地址、联系人、电话、明细、税率、备注全部带过去
- 合同 → 一键「转送货单」：客户与明细带过去，并写入关联合同号
- 单据详情页顶部以**流程图**展示整条业务链：报价单在左，销售合同在中间分支，送货单接在对应合同右侧；同一报价可挂多张合同、同一合同可挂多张送货单，点任意节点跳转
- 报价单直接生成的送货单统一放在第三列送货单位置，不和销售合同挤在同一列；如果链路上已经存在送货单，再点“转送货单”会提示确认，继续生成时自动使用未占用编号，不会重复单号
- 工作台自动列出「报价未转合同」「合同未送货」的待跟进单据

**文件库**
- 单据附件（合同扫描件、发票、送货回单）、公司 Logo、电子章
- 上传、在线查看、下载、按类别筛选；文件落盘在 `data/files/年-月/`，元数据在数据库

**仓库打单（v1.8 / v1.8.1）**
- 新增 `warehouse` 仓库角色，仅管理员和仓库账号可进入“仓库打单”页
- 仓库账号登录后直接进入仓库打单，侧栏只保留“仓库打单”；不显示工作台、单据中心、客户档案、货品库、文件库、回收站和系统设置，可手动新建送货单，但不能新建报价单或合同
- 业务员只负责提交/撤回送货单，提交后、仓库接收前不能编辑；接收、编辑、打印、完成只有仓库账号可以操作，管理员进入仓库页只能只读查看队列
- 业务员在送货单详情点“交仓库”，送货单进入共享待接收队列；仓库可直接打印待接收单（打印时自动接收为“处理中”），也可接收后编辑、打印，完成后标记“已完成”
- 仓库不接收业务员单据时，也可以在“仓库打单”页点“新建送货单”，直接手动开单；保存后自动进入“处理中”，可继续编辑、打印、完成
- 提交人可在仓库接收前撤回；仓库编辑不改变单据归属，仓库也不能改业务状态或派生新单据
- 仓库跨账号仅能访问已提交的送货单，客户、报价单、合同等数据仍按账号隔离

**回收站（v1.8）**
- 单据和文件删除改为软删除，先进入回收站，保留 30 天
- 本人可删除自己的单据、文件，管理员可删除任意成员的数据；管理员可在回收站按成员筛选
- 回收站内可恢复；也可立即永久删除，不可再恢复
- 超过 30 天的条目由服务在启动时和每 6 小时自动物理清理；单据附件实体不会随单据删除立即消失，避免误删文件库

**旧数据迁移**
- 系统设置里直接导入三个旧工具导出的 JSON 备份，客户 / 货品 / 单据去重导入

## 三、快速开始（Windows）

1. 确认 Node.js ≥ 22.13（内置 SQLite 默认开启）：`node -v`
2. 双击 `启动.bat`，或命令行：
   ```powershell
   cd D:\dbwork\集中管理系统
   node server.js
   ```
3. 浏览器打开 http://localhost:8099
4. 默认管理员用户名 **admin**，免密码登录；普通用户可在登录页自助注册中文用户名

完整的 Windows 环境要求、局域网访问、防火墙、开机自启、升级与备份步骤见 [`docs/部署说明.md`](docs/部署说明.md#二windows-部署)。

数据目录默认是项目下的 `data/`（可用环境变量 `DATA_DIR` 指定）：

```
data/
├── app.db          SQLite 数据库（用户、客户、货品、单据、文件元数据）
├── secret.key      登录令牌签名密钥（自动生成，勿外传）
└── files/          上传的文件（按 年-月 分目录）
```

## 四、Docker / NAS 部署

```bash
# 把整个目录放到 NAS（如 /vol1/1000/docker/jizhong）
cd /vol1/1000/docker/jizhong
docker compose up -d --build
# 打开 http://NAS的IP:8099
```

`docker-compose.yml` 已把 `./data` 挂到容器 `/app/data`，重建容器数据不丢。
端口 8099，和旧的 8090（报价单）/ 8091（合同）/ 8088（送货单）不冲突，可以并存过渡。

飞牛 fnOS 逐步部署（源码构建 / 镜像导入、迁移、更新、备份、常见报错）见 [`docs/部署说明.md`](docs/部署说明.md#一docker-部署飞牛-fnos)。

需要“推 tag 自动构建镜像、飞牛自动更新”时，用仓库里的 `.github/workflows/docker-release.yml` + `docker-compose.ghcr.yml`：推 `v*.*.*` tag 后 GitHub Actions 构建双架构镜像到 GHCR，飞牛上的 Watchtower 每 5 分钟检查并拉取新 `latest`。完整步骤见 [`docs/部署说明.md`](docs/部署说明.md#8-github-tag-自动构建--飞牛自动更新可选)。

生产建议在 compose 里固定 `APP_SECRET`（任意长随机串），否则重建容器会让所有人重新登录一次。

## 五、备份

只需要备份 `data/` 整个目录：

```powershell
# Windows 示例：停服后复制
Compress-Archive -Path .\data -DestinationPath "D:\backup\jizhong-$(Get-Date -Format yyyyMMdd).zip"
```

- 数据库是单文件 `app.db`（WAL 模式，运行中复制请连同 `app.db-wal`、`app.db-shm` 一起）
- 文件是普通文件，直接拷 `data/files`
- 恢复：把 `data/` 放回原位再启动即可

## 八、主要接口

所有接口以 `/api` 开头。除登录、注册、`/api/auth/guest`、`/api/public/bootstrap` 外，都需要身份：登录用户用 `Authorization: Bearer <token>`，游客用持久化 cookie `gid`（也可用 `?token=` 传登录 token）。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | `{username}` 免密码登录；若带游客 cookie，合并该游客数据 |
| POST | `/api/auth/register` | `{username,name,phone}` 公开注册，默认业务员，注册后直接登录并合并游客数据 |
| GET | `/api/auth/guest` | 临时游客：发/复用持久化 cookie `gid`，返回临时游客身份 |
| GET | `/api/auth/me` | 当前用户 |
| GET/POST/PUT/DELETE | `/api/users` | 用户管理（管理员）；新增/编辑不再需要密码 |
| GET | `/api/owners` | 管理员成员列表（含已有数据的游客），用于工作台/单据筛选 |
| GET | `/api/companies` | 公司主体 |
| PUT | `/api/companies/:id` | 修改主体（主管以上） |
| POST | `/api/companies/:id/logo\|stamp` | 上传 Logo / 电子章 |
| GET/POST/PUT/DELETE | `/api/customers` | 客户档案；按 `created_by` 隔离，管理员可加 `?owner=` |
| GET/POST/PUT/DELETE | `/api/products` | 货品库；全系统共享，仅创建人可修改/删除，管理员可按 `owner` 筛选查看 |
| GET | `/api/documents` | 单据列表（type/status/q/日期/分页；管理员可加 `owner`） |
| POST/PUT/DELETE | `/api/documents` | 新建 / 修改 / 删除；删除为软删除，进入回收站 |
| POST | `/api/documents/:id/warehouse` | `{ "action": "send" \| "withdraw" \| "receive" \| "done" }` 仓库流转 |
| GET | `/api/warehouse/deliveries` | 仓库待接收 / 处理中 / 已完成送货单队列（管理员与仓库角色） |
| GET | `/api/recycle` | 回收站单据与文件列表，返回剩余保留天数；管理员可加 `?owner=` |
| POST | `/api/recycle/documents/:id/restore` | 从回收站恢复单据 |
| POST | `/api/recycle/files/:id/restore` | 从回收站恢复文件 |
| DELETE | `/api/recycle/documents/:id` | 立即永久删除回收站单据 |
| DELETE | `/api/recycle/files/:id` | 立即永久删除回收站文件 |
| POST | `/api/documents/:id/convert` | `{ "to": "contract" \| "delivery" }` 派生下游单据，归属保持原单据 owner |
| POST | `/api/documents/:id/status` | 状态流转 |
| GET | `/api/documents/:id/chain` | 关联链路 |
| POST | `/api/documents/:id/files` | 上传附件（multipart），文件归属单据 owner |
| POST | `/api/files` | 上传到本人文件库 |
| GET | `/api/files/:id/raw\|download` | 查看 / 下载；公司 Logo/电子章全公司可读 |
| GET | `/api/dashboard` | 工作台统计；普通用户只统计本人，管理员可加 `?owner=` |
| GET | `/api/export/backup` | 导出结构化数据 JSON（主管以上；按本人或 `owner` 过滤） |
| POST | `/api/import/legacy` | 导入旧工具备份 JSON，数据归当前账号 |

## 九、和旧工具的关系 / 当前边界

三个旧项目（`SalesContract` 销售合同、`Contract-Generator` 报价单、`delivery-note-generator` 送货单）继续保留，可作为「断网应急」的单机版；日常统一用本系统。

当前版本覆盖了开单、联动、打印、客户/货品/文件/账号管理，**暂未搬运**的旧功能：

- 明细表列宽拖拽、三块字号微调（版式目前是固定的一套）
- 直接导出可编辑 `.docx`（现在走浏览器打印 / 另存 PDF）
- 送货单默认使用 **214.7×139.8mm 三联纸**（针式打印机），也可在模板里切 A4；明细默认 7 列：序号、存货编号、存货名称、规格型号、单位、数量、项目编号
- 电子章的上传去白底处理（现在是上传原图直接用，建议上传已去底的 PNG）

这些都在 `docs/系统设计.md` 的「后续演进」里列了优先级。

## 十、常见问题

**打不开页面**：确认 `node server.js` 窗口还在、8099 端口未被占用（`netstat -ano | findstr 8099`）。

**管理员账号登不进**：确认用户名是 `admin`（登录不校验密码）；若被停用，停服后用 SQLite 把 `users` 中 admin 的 `active` 改回 1。不要删 `app.db`，那会把所有数据一起删掉。

**打印出来有空白第二页**：送货单默认三联纸：打印面板纸张选「三联纸 214.7×139.8mm」（系统里可能显示为 21.47×13.98cm）、缩放 100%、边距「无」、关闭页眉页脚；报价单和合同选 A4。

**同事看不到我上传的章**：章存在服务器（公司主体里），所有人共用；旧工具是存在各自浏览器里的，这点已经改了。
